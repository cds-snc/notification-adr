# API access to delivery reports

Date: 2026-05-04

## Status

**DRAFT**.

_VALUES: (DRAFT, IN REVIEW, APPROVED, REJECTED)_.

## Related ADRs

None.

## Context

GC Notify already lets logged-in users request a CSV "delivery report" from
the Admin UI (sent messages / failures / a specific bulk job). We aim to bring the report
download functionality to the API so clients can pull delivery results into
their own system without scraping the dashboard or polling `/v2/notifications` page-by-page. 

This addition is part of a [broader ongoing initiative](https://app.zenhub.com/workspaces/notify-planning-614b3ad91bc2030015ed22f5/issues/gh/cds-snc/notification-planning/3077) to improve UI/API feature parity.

<details>
<summary>How the UI flow works today</summary>

1. **Request.** User clicks "Prepare report" in Admin. Admin calls
   [`POST /service/<service_id>/report`]((https://github.com/cds-snc/notification-api/blob/main/app/report/rest.py#L20)) on the internal API with the report
   type (`sms` | `email` | `job`), language, optional status filter, and
   optional `job_id`. See
   [app/report/rest.py].


2. **Persist + queue.** The API inserts a [`Report`]((https://github.com/cds-snc/notification-api/blob/main/app/models.py#L2783-L2784)) row with status `requested` to the DB and dispatches the 
   [`generate-report`](https://github.com/cds-snc/notification-api/blob/main/app/celery/tasks.py#L888-L889) Celery task to the `GENERATE_REPORTS` queue.


3. **Generate.** The Celery worker [streams the result](https://github.com/cds-snc/notification-api/blob/main/app/report/utils.py#L250-L251) of a Postgres
   `COPY ... TO STDOUT` directly into S3 at
   `reports/<service_id>/<report_id>.csv`, stores a presigned URL on the
   row, sets `status=ready`, and sends a "your report is ready" Notify
   email to the requesting user.


4. **Poll.** [Admin polls `GET /service/<service_id>/report`](https://github.com/cds-snc/notification-admin/blob/main/app/main/views/reports.py#L53) 
   every 5s via an
   [`ajax_block`](https://github.com/cds-snc/notification-admin/blob/main/app/templates/views/reports/reports.html#L22) to refresh the table.


5. **Download.** When `status=ready`, Admin's 
   [`main.download_report_csv`](https://github.com/cds-snc/notification-admin/blob/main/app/main/views/reports.py#L99) route 
   [**proxies** the S3 object](https://github.com/cds-snc/notification-admin/blob/main/app/s3_client/s3_csv_client.py#L84) 
   through Admin in 1 MB chunks rather than redirecting the browser to the presigned URL.


6. **Expire.** Reports are deleted from S3 72 hours after they are ready
   (`DAYS_BEFORE_REPORTS_EXPIRE`).

</details>

### Constraints carried over to the API

- Reports can be large (millions of rows) — generation is async and likely should
  stay async.
- A report must only be downloadable by the service that owns it.
- We must not break the existing Admin flow.
- Usage should be auditable. (Caveat: API keys can only identify the service but not the user)

### Decision drivers

1. Lowest risk to the existing Admin flow.
2. Smallest new surface area to maintain (auth, rate limits, infra).
3. Familiar idioms for API consumers.
4. As much reuse of existing `Report` model, Celery task, and S3 layout as possible

## Options

### Option 1 - REST: request → poll → download (mirrors the UI)

Expose three new endpoints under `/v2/reports`:

| Verb   | Path                              | Purpose                              |
| ------ | --------------------------------- | ------------------------------------ |
| `POST` | `/v2/reports`                     | Request a new report                 |
| `GET`  | `/v2/reports/<report_id>`         | Get status + download URL when ready |
| `GET`  | `/v2/reports`                     | List recent reports for the service  |

`/v2/reports` returns `202 Accepted` with the report id and a `Location` header
pointing at the status endpoint. When `status=ready`, the status payload
includes either:

- **1.a** A short-lived **presigned S3 URL** the client `GET`s directly, or
- **1.b** A **streaming download endpoint** on the API
  (`GET /v2/reports/<report_id>/content`) that proxies S3 the same way
  Admin does today.

**Pros**

- Simplest to implement, we can reuse existing DAO, Celery task, and S3
  layout.
- Standard REST polling is well understood by API consumers; works with
  every HTTP client, no extra deps.
- 1.a offloads bandwidth from our infra; 1.b keeps all auth/audit on our
  side and avoids leaking S3 details.

**Cons**

- Clients must poll. This is fine for low volumes but adds load if hundreds of services poll concurrently.
  - An opt-in callback webhook could be made available for high-volume services with the dev capacity to consume them
- Two-step download (status → URL) is less convenient than a single blocking call.


### Option 2 — Single blocking endpoint that streams the CSV

`GET /v2/reports/sms?status=delivered&days=7` returns the CSV directly,
generated on the fly using Flask's
[streaming response](https://flask.palletsprojects.com/en/stable/patterns/streaming/)
backed by the same 
[`COPY TO STDOUT` cursor](https://github.com/cds-snc/notification-api/blob/main/app/report/utils.py#L205) 
used today.

**Pros**

- One call, no polling, no S3 round-trip.
- Feels like a normal API - "give me my data".

**Cons**

- Holds a Gunicorn worker open for the entire duration of the export.
  A 10-million row CSV can take minutes; this could starve our gevent worker capacity and risk load-balancer / API gateway timeouts.
- No retries - if the connection drops at 80%, the client starts
  over and we re-run the query.
    - This is more expensive compared to option 1 where the generated report is stored in S3 for a time.
- Hard to audit correctly - no persistent artifacts makes resue of the `reports` table challenging as it is structured with persistence in mind.
- Hard to rate-limit fairly — a single big export looks the same as a
  dozen small ones.

### Option 3 — WebSockets / Server-Sent Events for progress

Use [`flask-socketio`](https://flask-socketio.readthedocs.io/) (or
plain SSE) to push status changes (`requested → generating → ready`)
and the final download URL to the client.

**Pros**

- No polling; instant notification when ready.
- Nice UX for long-running reports.

**Cons**

- New runtime dependency and infra: `flask-socketio` [requires a message
  broker](https://flask-socketio.readthedocs.io/en/latest/intro.html#:~:text=If%20using%20multiple%20processes) (Redis) **and** sticky sessions or a
  socket.io-aware load balancer.
- The current API is a stateless, sychronous, request/response service; WebSockets introduces long-lived connections and event-driven programming, complicating error handling, resource management, and deployment infra - it's a different operational model for us as well as our clients
- Most API consumers are likely to be server-to-server code/scripts (e.g. cron jobs, ETL,
  Power Automate flows) where a WebSocket client is awkward. They
  may end up writing a polling loop anyway.
- Overkill: The cost/benefit is poor compared to polling or a callback webhook.

## Additional considerations

- **Rate limiting.** `POST /v2/reports` should be capped per service
  (10/hour?) to prevent a misbehaving client from queueing
  thousands of large exports.
- **Email on completion.** API-initiated reports should *not*
  send the "report ready" email when the request is API-initiated as
  we cannot determine which user made the call from the API key alone
- **Cleanup.** The existing 72h S3 cleanup task already keys off the
  `reports` table schema, so API-created rows are covered.
- **Documentation.** Will require OpenAPI updates and a disclaimer about the endpoints absence from the GDS API client libraries.
- **Audit.** Proxying the download (Option 1.b) gives us per-download
  log lines tied to the API key; presigned URLs (1.a) do not.

## Decision

**Adopt Option 1.b:** request → poll → download, with the download
proxied through the API.

Concretely, add these new endpoints to the `/v2` API:

| Verb   | Path                                | Notes                                                |
| ------ | ----------------------------------- | ---------------------------------------------------- |
| `POST` | `/v2/reports`                       | Body mirrors the internal endpoint.                  |
| `GET`  | `/v2/reports`                       | Paginated list scoped to the calling service.        |
| `GET`  | `/v2/reports/<report_id>`           | Status + metadata. `download_url` set when `ready`.  |
| `GET`  | `/v2/reports/<report_id>/content`   | Streams the CSV from S3 in chunks (same as Admin).   |

Auth: existing service JWT (`requires_auth`). All endpoints scope by the
authenticated `service_id`; cross-service access returns `404`.

Why 1.b over 1.a: streaming through the API keeps a single auth model,
gives us per-download audit logging, and avoids handing out S3 URLs that
may outlive a revoked API key. The bandwidth cost is bounded by the 72-hour
expiry and the existing report size.

We **reject** Option 2 because it ties up workers and breaks at our
infra timeouts. We **reject** Option 3 because the operational cost of
WebSockets is not justifiable; if desire for push semantics is strong enough then a callback webhook
could be considered as it is a simpler solution.

## Consequences

**Positive**

- The existing infra: `Report` model, Celery task, S3 layout, and
  expiry job can be reused.
- Public API contract is independent of the internal one; both can evolve
  without breaking integrations.
- Polling load is bounded by a documented minimum interval
  (`Retry-After: 10`?).

**Negative / follow-ups**

- New per-service rate limit on `POST /v2/reports` to add and tune.
- OpenAPI + client-library docs to publish before announcing the
  feature.
- Need a small branch in the Celery task to skip the "ready" email
  when `requesting_user_id` is null.

**Future work**

- If client demand justifies it, add an **opt-in webhook**
  ("report ready" → POST to a service-configured callback URL). This
  is the natural async-push story for server-to-server clients, is
  much cheaper to operate than WebSockets, and our clients are already familiar
  with them via notification callbacks.
- Revisit Option 2 as a `GET /v2/reports/quick` for small, bounded
  exports (e.g. last 24 h, capped at N rows) once we have data on
  typical request sizes.
